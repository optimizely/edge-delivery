# Edge Delivery from KV

A Cloudflare Worker that runs Optimizely Web experiments at the edge using
[`@optimizely/edge-delivery`](https://www.npmjs.com/package/@optimizely/edge-delivery),
reading the Edge Delivery config from a **Cloudflare KV namespace** instead of the CDN.

When `kvNamespace` is provided and `DATA` is omitted, the SDK loads the config from KV
using `snippetId` as the key. This is useful when you push config to KV yourself (for
example from a webhook) rather than fetching it from the Optimizely CDN.

## Prerequisites

- A [Cloudflare account](https://dash.cloudflare.com/sign-up/workers-and-pages).
- The [Wrangler CLI](https://developers.cloudflare.com/workers/wrangler/).

## Configuration

Worker variables and bindings live in [`wrangler.toml`](./wrangler.toml), split into a
`dev` and a `prod` environment:

| Name                    | Kind       | Description                                                          |
| ----------------------- | ---------- | ------------------------------------------------------------------- |
| `SNIPPET_ID`            | var        | Used as the KV key the config is stored under and read from.        |
| `environment`           | var        | `'dev'` or `'prod'`. `dev` enables local seeding and `dev_host`.    |
| `dev_host`              | var        | The host to proxy when developing locally.                          |
| `EDGE_DELIVERY_CONFIGS` | KV binding | The KV namespace holding the config, keyed by `SNIPPET_ID`.         |

Create a KV namespace and copy its id into the `id` fields in `wrangler.toml`:

```bash
wrangler kv namespace create EDGE_DELIVERY_CONFIGS
```

The full list of SDK options is documented on the
[npm package page](https://www.npmjs.com/package/@optimizely/edge-delivery).

## How the config gets into KV

- **Local dev:** the KV store starts empty, so [`src/index.ts`](./src/index.ts) seeds it
  once from [`src/seed-data.json`](./src/seed-data.json) when `environment === 'dev'`.
  Replace `seed-data.json` with your own snippet's config.
- **Production:** an Optimizely webhook keeps KV up to date automatically (recommended —
  see below). You can also populate it manually at any time:

  ```bash
  wrangler kv key put --binding=EDGE_DELIVERY_CONFIGS "<SNIPPET_ID>" --path ./src/seed-data.json --env prod
  ```

## Auto-updating KV with an Optimizely webhook (recommended)

Instead of pushing config to KV by hand, let Optimizely notify the worker whenever the
Web SDK artifact changes. The SDK handles this for you: when a webhook `POST` arrives
(identified by the `X-Optimizely-Event-Type: WebSDKArtifactUpload` header), it verifies
the signature and writes the new config to KV — all inside `applyExperiments`, so there's
no extra request handling in `index.ts`.

To enable it you only need to provide `webhookSecret` (this template already passes it from
`env.WEBHOOK_SECRET`). The secret is generated by Optimizely when you create the webhook —
you copy it from there into the worker:

1. **Deploy the worker** and note its public URL/route (e.g. `https://your-site.com/`).
   Optimizely posts to the worker's normal URL — there is no special webhook path.
2. **Create the webhook in your Optimizely Web project's webhook settings:**
   - Enter the worker URL from step 1 as the destination.
   - Save it, then **copy the webhook secret/key** that Optimizely displays for the webhook.
     This is the value used to sign requests (sent as the `X-Hub-Signature` header).
3. **Store that secret in the worker** as an encrypted Wrangler secret — paste the value
   copied from Optimizely when prompted (do **not** put it in `wrangler.toml`):

   ```bash
   wrangler secret put WEBHOOK_SECRET --env prod
   ```

Once configured, publishing changes in Optimizely triggers a webhook that refreshes KV, and
the next page request serves the updated config. Manual seeding is then only needed for local
development.

## Run locally

```bash
npm install
npm run dev
```

## Deploy

```bash
wrangler login
npm run deploy
```

Then add a [route](https://developers.cloudflare.com/workers/configuration/routing/routes/)
for the worker on the website you want to run experiments on.
